## 1. 难度曲线为什么回到了「一条」

**问题（三层，一层比一层深）。**

第一层：难度原本是单条指数 `1.56^(f-1)`，211 层到 `3.6e40`。怪物血量跟着它走时会撞上两个东西——第 33 层就撞到 `1e15` 的防溢出闸门，于是第 33 到第 211 层的怪**数值一模一样**，后期没有强度曲线，只有一条被钳平的直线。

第二层：玩家的成长在很早就全部封顶（攻击第 11 层、轨迹伤害第 21 层、轨迹宽度第 20 层）。之后每 20 层环比都是 **×1.00**，而难度是 **×7290/20 层**。玩家的数值从第 21 层起就是装饰品，活下来靠的是少数几个跟着难度缩放的伤害源。

第三层：v9.31 的处理办法是**再拉一条尺子**——难度 `D` 仍然是 `1.56^(f-1)`（HUD 上那个数），另造一个只给怪物用的 `S`，60 层后改成线性。这修好了数值，但留下一个说不清的缝：**屏幕上写着「难度 ×2.48e11」，实际打的那只怪只有 ×2.5e11**——两个数在 60 层之后就是两回事，且永远对不上。

**现在的设计。** 不再打补丁，换掉曲线本身。三次多项式**本身就不爆炸**，于是「收紧尾巴」这件事不需要了，两条尺子自然并回一条：

```
D(f) = S(f) = 1 + 0.3365x + 0.0566x² + 0.0063x³        x = f − 1
```

第 1 层 ×1.00 / 10 层 ×13.2 / 30 层 ×212 / 50 层 ×895 / 100 层 ×6.70e3 / 211 层 ×6.09e4。

- HUD 上的「难度 ×」、对局记录里的 `diff`、怪物的 HP 与攻击、BOSS 血量，**现在是同一个数**。对局记录里的 `ms` 列保留但恒等于 `diff`。
- 八个消费方（`spawnMonster` / `spawnDebugMonster` / `getBossAtk` / `spawnBossMinion` / E10 反噬 / 终结技 / `activateEliminate()` / 爆裂词缀新星）一个都没改，`getMonsterScale()` 退化成 `getDifficultyMultiplier()` 的别名——它们要的本来就是「这一层的强度标尺」，不是「哪条曲线」。

**⚠️ 代价：后期大幅变简单。** 211 层从 `3.6e40` 降到 `6.09e4`——低了 36 个数量级。这是这条曲线的**预期结果**，不是 bug：晚期的难度现在全部由三次项提供，而不是由一个失控的底数提供。试玩时要盯的是「后期会不会太软」，而不是「数值对不对」。

**⚠️ 陷阱：`x = f − 1` 那个偏移。** 它是「第 1 层 ×1.00」的唯一来源。写成 `x = f` 会让第 1 层从 ×1.34 起步，整条前期的底数全变。常数项那个 `1` 也不能省。

**⚠️ 陷阱：`getBossHp()` 的尾巴钳子。** 尾巴那一项写成 `D(f) / D(DIFF_KNEE)`：

```js
tail = (G.floor <= DIFF_KNEE) ? 1 : getMonsterScale() / diffScaleAt(DIFF_KNEE);
```

`f ≤ 30` 那道 `1` **不能丢**。丢了之后第 10 层会算成 `D(10)/D(30) = 0.062`，BOSS 血量直接软掉 **16 倍**——而且它不会报错，只会让前十层的 BOSS 变成纸糊的。

**这条曲线**保留了「BOSS 与普通怪的血量比恒定在 ~29.5 倍」这个性质：`tail` 与普通怪吃的是同一条曲线，所以比值不随层数漂移，任何层数都不会出现「BOSS 反而不如一只精英肉」。

**⚠️ 陷阱：`DIFF_KNEE = 30` 现在什么都不是。** 它不是拐点（三次曲线处处平滑）。它只是「前期 / 后期」的分档线，被四处共用：`getEssenceCap()`、清层卡数修正、`EARLY_NORMAL_MUL` 生效范围、`getBossHp()` 的尾巴钳位。动了它，四处都会跟着动。

**不吃标尺的，以及为什么：**

- `scoreValue`（分数）——它不是战斗数值，而且上 lg 显示。
- `06-render.js` / `07-ui.js` / `10-sim.js` 的难度**显示**、快照的 `difficulty` 字段。
- **`getTrailDamage()`**——它仍是**平值**（`buffs.trailDmg + log2(f+1) × 0.5`）。乘标尺会让第 21 层变成一击必杀（`103 × 7290` 打 `8 × 7290` 的怪），等于把整个早期手感推倒重来。代价是：**踩轨迹在后期依然是装饰性的**，后期的胜负由那四个核弹（终结技 / R 消除 / E10 反噬 / 爆裂词缀）决定。这是有意欠下的债，还没还。

## 2. 溢出闸门只是闸门

**问题。** 早先那三道钳子（怪血 `1e9`、怪攻 `120`、`min(D^0.35, 12)` 的 12）是照一条多项式曲线调出来的。换成指数曲线之后，它们在第 17 / 37 / 44 层就会被撞到——撞到之后怪**不再变强**，等于曲线被拦腰截断。

**现在的设计。** 它们是纯防溢出：怪血与 BOSS 血 `1e15`、怪攻 `1e9`、怪移速 `6.0`。配合三次曲线，第 211 层也只用掉 `1e15` 那道闸门的千分之一。

**⚠️ 陷阱。** 闸门仍然与曲线耦合——改了系数就要重算它们的适用楼层。定低了就会重演「曲线被截断」。反过来说：**任何一局真的撞到 `1e15`，都说明曲线本身已经失控**，该改的是曲线不是闸门。

**为什么 `atk` 的幂次是 0.35 而不是 4.0。** 用 4.0 的话怪物伤害会在第 10 层左右永久冻结在一个值上，之后再怎么加层都不变。0.35 让攻击随层数缓慢但持续地涨。

## 3. 数值上限为什么要是软的

**问题。** 玩家侧的上限原本是一批死数字（攻击 250、轨伤 100、轨宽 150……）。它们都在 20 层前后被撞满，之后玩家的数值曲线是平的——见 §1。

**现在的设计。**

```js
PLAYER_CAP_RATE = 0.015;
playerCap(base) = base * (1 + G.floor * PLAYER_CAP_RATE);
```

第 1 层 ×1.015、100 层 ×2.5、**200 层 ×4**。三个消费方（E06 轨伤 / E06 轨宽 / E11 移速）与商店里同语义的两条（轨迹淬炼 / 轨迹拓宽 / 疾步）全部走它。

**⚠️ 但「攻击力」这条轴上，「上限」这个概念被整个删掉了。** `E01` 的 `atkUp`、`E02` 的 `multUp`、商店「攻击强化」三条路径现在都是**无上限累加**——原来的 `playerCap(250)` / `playerCap(49)` / `playerCap(2000)` 全部撤掉。

为什么这条轴要单独放开：攻击力是**乘法区**的入口（`(atk + atkUp) × (1 + multUp)`），它每加一点都会被倍率、命运加成、暴击放大一次。给它一道软上限，等于给整条输出曲线装了一个天花板；而软上限随层数涨的速率（`×0.015/层`）远低于怪物血量的涨速，最终还是会被撞上。既然要放开，就彻底放开——**成长速度（拿牌频率）就是它的上限**。

**⚠️ 陷阱：解构 `playerCap` 的三条路径都要一起改。** 它们分散在 `02-combat.js` 的 E01/E02 两个 case 与 `00-data.js` 的 `STAT_CHOICES` 里，漏掉一处就是「有的路能涨、有的路卡死」，玩家只会觉得这条轴坏了。

**为什么还有三个例外写死。** `RARE_E15_CAP` 30、玩家护盾上限 300、`fireRateMul` 2.0 不动——射速抬到 8 倍会直接把攻速玩坏，另外两个也不在这次的轴上。

**⚠️ 陷阱：轨迹宽度那条「只增不减」。** 原本的写法是 `trailWidth = Math.min(trailWidth + 1, 60)`。轨宽到 150 之后再去拿「轨迹拓宽」，`Math.min(151, 60)` = 60，**净亏 90**——不是不涨，是往回砍。实测里它出现过四次（150 → 60），前三次靠后续 E06 触发爬回来，第四次撞上一次正常的被动移除（`60 - 6 = 54`），此后一百多层都只有 54 宽。

现在 E06 与商店「轨迹拓宽」**共用同一个上限** `getTrailWidthCap()`，并且写成只增不减：

```js
G.buffs.trailWidth = Math.max(G.buffs.trailWidth,
    Math.min(G.buffs.trailWidth + 1, getTrailWidthCap()));
```

**E11 原本根本没有上限**，是这次补上的：`Math.min(..., playerCap(6))`。基准取 6 的理由是它在 211 层约 ×25，而实测的极端值只有 ×17.7——不会误伤现状，只是加一道安全阀。

## 4. 射速：两道闸门与「隔层快一倍」

**问题。** 射速由两个互不认识的数控制，实际间隔不是它们的和，而是**「≥ 冷却的 `fireRate` 最小整数倍」**：

```
G.fireRate      = 40                                // 每几帧「问一次」
p.shootCooldown = max(24, 48 - f × 0.32) / 1.2      // 冷却「好了没」
```

射速闸每满 `fireRate` 帧才问一次冷却，冷却没走完就白问一次（`fireCounter` 已归零）。于是：

```
冷却 ≤ fireRate          → 间隔 = fireRate
fireRate < 冷却 ≤ 2×fr   → 间隔 = 2 × fireRate
```

**现在的设计。** 冷却上限 `48 / 1.2 = 40` 恰好等于基础 `fireRate`，所以 `冷却 ≤ fireRate` 恒成立——**基础职业全程稳定 40 帧一发**，「隔层突然快一倍」那层结构消失了。只有职业改了 `fireRate` 时冷却才重新起约束：弹幕风暴 `fireRate ×0.6 = 24`，第 1 层冷却 39.73 → 间隔 48（`2 × 24`）。

**⚠️ 陷阱。** `PLAYER_FIRE_RATE_MUL` 要除**整条表达式、包含 `Math.max(24, …)` 的地板**。只除一半，高层会出现「地板反而比公式值大」的倒挂。

**⚠️ 第二个两道闸门：`G.buffs.fireRateMul`**（E17 急速装填）。它同时出现在 `p.shootCooldown`（`04-trail.js`）和 `G.fireCounter >= G.fireRate / G.buffs.fireRateMul`（`05-update.js`）里。只改一处不生效；它只在 `resetGame()` 里复位。

## 5. 承伤：一个出口，两种例外

**问题。** 「只扣护盾、护盾破了继续咬核心、飘字颜色各不相同」这套结算原本在八处各写各的。

**现在的设计。** 全部收敛到 `damagePlayerSide(dmg, opts)`（`05-update.js`）。收敛时**各处的飘字颜色与位置原样保留**（火圈橙、敌图腾橙、撞核心红）——别顺手统一成一个色，那是给人读的战斗信息。

| `opts` | 作用 |
|:--|:--|
| `shieldOnly` | **只作用于护盾**，护盾归零后停手、不咬核心 |
| `silent` / `noText` / `particles` | 给逐帧来源（火焰轨迹、危险区）降噪 |

**⚠️ 荆棘和火圈是相反的。** 荆棘是 `shieldOnly: true`（点名要求：荆棘只作用于护盾），火圈那类才是「护盾破了继续咬核心」。全项目 `shieldOnly: true` 恰好 **2 处**。

**伤害不跨池溢出**：护盾 50 挨一记 60，结果是护盾 0、核心 100（第二记才扣核心）。这条是原本手写规则就有的行为，收敛到 helper 时**原样保留**。

怪物撞核心那处额外的 `Tutorial.emit('hit')` 与 `breakKillStreak()` 留在调用点，**不进 helper**——它们不是血量结算。核心归零的死亡判定也不在这里。

## 6. 减速：三套机制重叠之后

场上同时有三套减速来源：

| 来源 | 载体 |
|:--|:--|
| 冰轨永冻 / 时间膨胀器 | `G.buffs.slowAll` |
| 踩轨迹 | `m.slowTimer`（180 帧） |
| E14 延缓 | `m.slowTimer`（30 / 60 帧 × n） |

**设计取舍：**

- **踩轨迹与 E14 共用 `m.slowTimer` 和同一个 0.8 乘数**，叠加时**取更长的持续时间，不叠乘**。
- **圈层重叠取最强（`Math.min`）而非连乘**——三只怪、三个圈叠在一起若连乘，玩家等于被冻住，那就超出「减速」的语义了。
- 轨迹**不阻挡怪物移动**（旧版是随机偏转 + 减速），只留迟缓。移除阻挡是刻意的：随机偏转有一半概率把怪推进墙里，而且围剿那套判定是**纯几何**的，和物理阻挡无关，所以取消阻挡不影响它。

**⚠️ 陷阱：`slowAll` 被乘了两次。** `speed` 在**生成时**已经乘过一次 `(1 - slowAll)`（`02-combat.js`），**每帧更新时**又乘一次（`05-update.js`）。所以实际效果是 `(1 - slowAll)²`——`slowAll = 0.7` 时其实只剩 0.09 的移速。改减速数值时要按平方算，别按一次算。`slowTimer`（踩轨迹 / E14）没有这个问题，它只在每帧那一处乘。

## 7. 密文板的层数语义

**问题。** 同一组「触发板 + 效果板」可以叠 n 层。原来的语义是「`triggerPassive` 把整个 switch 重跑 n 遍」，于是有的效果叠得动、有的叠不动、有的叠到一半被截断。

**现在的设计。** 按类别写死：

```js
const PASSIVE_REPEAT_EFFECTS = new Set(['E02', 'E06', 'E10', 'E11', 'E12']);  // 触发次数 ×n
// 其余全部：一次结算，数值 / 时长 ×n
```

- `applyPassiveEffect(..., layerCount)` 的第五个参数默认 1；`addPassive()` 传 1——**组合那一刻只生效一层**，层数由后续触发累加。
- **⚠️ 两边都乘就是 n²。** 留在循环里又在 case 里乘一遍，是这条改造最容易踩的坑。往集合里加 id 之前，先确认它的 case **没有**再乘 `layerCount`。
- `E12` 维持「一次触发一条链」是**有意保留**，不是漏改。

**⚠️ T03 的 ×1.2 与回退必须同步。** `applyPassiveEffect()` 里每个写数值/时长的 case，和 `removePassive()`（`07-ui.js`）的四处回退，都要乘同一个 `T03_EFFECT_MUL`。只加一边，表现是移除被动后 `G.buffs.atkUp` 变成负数或留下残值。

**⚠️ `_layerCCTick` 的标记规则。**

- E13 / E14 且 `layerCount > 1` 时给命中的怪打标记，它每秒额外吃 **100% 玩家攻击力**。
- 标记**只能**由 E13 / E14 且 `layerCount > 1` 设置。**轨迹接触造成的 `slowTimer` 绝不能碰它**——否则平 A 铺轨就白送 DoT。
- 结算位置**必须**挂在计时器递减紧后面、移动块**之前**：冰冻中的怪跳过了移动块但**仍然会跑轨迹伤害块**，挂在后面就成了「冰冻中打得更多」。
- 脱控（`!frozen && !slowTimer`）即清标记。

**为什么 E13 / E14 要看命中目标。** 原来 E13 是「全场 65% 概率逐只掷骰」、E14 是「全场」，两者都不看命中目标。现在的作用范围是「命中目标 + 它周围 225px 内的怪」；没有目标的触发器（T10 残血 / T12 闭环 / T14 唤魔者）就近兜底取离玩家最近的那只怪；场上无怪则空放。

## 8. 消除为什么从卡牌变成技能

它原来是一张触发板，代价是「烧掉两张牌」。问题是：**抽到与否纯看运气，而它的效果量级（清场 + 拆塔）足以决定一波团战。** 挂在随机掉落上，等于把节奏交给抽卡。

变成带冷却的技能（`R` / 手机端 🧹 圆钮，30 秒）之后，**什么时候按成了玩家的决策**。效果是 3 倍反噬 + 拆掉最早的一座塔；场上无塔时照样造成伤害，只是不拆。

## 9. 唤魔者为什么是一次性宣读

**问题。** 唤魔者（T14）原本走 `addPassive()` 这条正常路径，于是：它**占掉一个被动槽位**，而 `triggerPassive('T14')` 在 `G.passives` 里找不到它就直接 return——**T14 永远不触发**。等于花一个槽位买了一张死牌。

**现在的设计。** `T14` 在 `doCombine()` 的**槽位检查之前**被单独接管：不受被动槽位限制、**不写 `G.passives`**（所以不占槽、也不参与槽位计数），两张牌宣读完即消失。槽位计数数的是 `G.passives[tid].length`，它不进去就天然不占位。

「两张牌都消失」不需要额外代码：`combineCards()` 在 `doCombine` 之后本来就会清空两个槽位，而 `fillSlot()` 放牌时已经把它们从手牌摘掉了。暂停排队的 `executeBatch()` 同理。

**其他几个刻意决定：**

- **清场不走 `registerKill()`。** 走了会加击杀数、加分、断连杀、触发 T08——等于白送一整套收益。所以只放粒子和 ☠ 飘字。
- **代价算的是清场前场上怪的数值之和**（先算再清）。杀不掉就一直挂着。
- **`getBossAtk()` 是单独抽出来的函数**，保证「该层 BOSS 的攻击」只有一个来源——原来那句 `45 × D^0.35 × bossEarlyMul()` 只写在 `spawnBoss()` 里。
- **顶不掉「每 10 层一只」。** `spawnBoss()` 本来就不碰 `G.bossPending` / `G.bossSpawned`（那是调用方的活），BOSS 死亡分支里那两个标志另有 `!m.isEvokerBoss` 守卫。
- **不会被自动宣读**：槽满自动宣读遍历的是 `G.passives`，`T14` 不在里面——唤魔者只能由玩家自己按。

**🗝️ 唤魔之钥**是 `RELICS` 里唯一 `hidden: true` 的一件：`dropRelic()` 直接跳过它，所以它只从唤魔者身上掉、不进随机池。它也不占遗物名额（`gainEvokerKey()` 直接 push，不走 `dropRelic()`）。

## 10. 精英词缀的几个非显然决定

**精英也抽得到 BOSS 专属词条，但只算半权**（`ELITE_BOSS_AFFIX_WEIGHT = 0.5`）。BOSS 池本身**一点没动**，仍是 12 条等权。

**⚠️ BOSS 池的洗牌是有偏的，但故意不动。** `pickAffixes()` 分了岔：`isElite` 走加权抽样，BOSS / 调试走 `[...pool].sort(() => Math.random() - 0.5)`——那条洗牌**是有偏的**（低索引容易留在前面）。但既有的 BOSS 分布就是照它测的，改「正」了会让分布漂移。**所以别拿频率去测 BOSS 池的「均匀」，要测就走结构断言。**

**圈层为什么从「贴身」改成「落点」。** 削弱 / 减速 / 火焰圈原来挂在 BOSS 自己脚下，而 BOSS 是 `alwaysMoving` 追着玩家跑的——等于「靠近 BOSS 就被永久削弱」，既不可躲也不好看。现在改成在场地上落一个静态圈（每 5 秒一个，半径 ×1.5，存活 6 秒，同属性同屏上限 3），落定后与 BOSS 位置再无关系，BOSS 走了圈还在。存在 `G.affixZones`（**不再挂怪身上**，`_affixZones` 里只剩牵引那一个环）。

**为什么火焰圈是 0.167/帧，不是照抄火焰轨迹的 0.8/帧。** 火焰轨迹是一条细线，站满 150 帧掉 120；换成 135px 的大圈活 360 帧，满吃 288 **直接秒杀**。现在穿过去（约半秒）掉 ~5 点、从头站到尾掉 60 点，能动就躲得开。

**其他：**

- **残影不带词条**（`affixes: []`）——否则词条会指数级扩散。
- **敌图腾不复用 `G.turrets`**，走独立的 `G.enemyTotems`，避免污染玩家的图腾上限与环 key。
- **封印只在玩家真有被动时才有意义**（没有可封的组合时这条词条是空的）；被封印的组合**不删除**，只是这 4 秒 `triggerPassive` 整条跳过。
- **圈层也作用于玩家图腾**：削减区砍单发伤害，减速区砍「出手速度」（塔不移动，同位置的动作频率就是它的速度），火焰区沿用火焰烧塔的速率。

## 11. 图腾为什么伤害现算

**问题。** 早先塔的伤害是**生成时的快照**，公式是 `d × m × (1 + D × 0.3)`。D 一高，连最基础的塔都能被推到几百点——塔变成了主角，而玩家自己的攻击力反而无关紧要。

**现在的设计。** 伤害在**开火时现算**：

```
dmg = getPlayerAttackPower() × 1.0 × t.ratio / 75 × getTurretAtkZoneMul(t)
```

- `d` 从「绝对伤害」变成「**相对权重**」——它只决定「同一玩家攻击力下这座塔比别的塔强多少」。
- 上限就是**玩家攻击力的 1.0 倍**，「大环闪电」正好顶到上限，其余按旧 `d × m` 比例往下排。比例关系没变，只是绝对值不再随难度指数膨胀。
- 现算而非快照的收益：玩家捡到攻击加成后，**场上的塔会立刻跟着变强**。
- 上限取 1.0 而不是 0.6：0.6 那一版塔的输出压得太狠，花 6 张牌换来的建筑打不过玩家自己平 A。

塔的定位是「**稳定的辅助输出 + 效果载体**」（冰冻 / 连锁 / 足迹）。「怪物的敌对建筑」单独算，伤害 `3 + f × 0.2`、**不吃玩家攻击力**——玩家的塔随玩家成长，敌人的塔只随层数变强，这是两种东西。

**判环**是纯几何：轨迹中点按网格吸附成节点，撞见重复节点且间隔够远即成环，鞋带公式算面积分档。

## 12. 手牌经济：为什么会有「槽满自动宣读」

**问题。** `maxSlots` 到 60 层封顶 7 个，之后手牌只能攒不能花。一局实测：**1476 张牌进账，只合成出 32 个被动——95.7% 的卡到手即废**，玩家后来连看都不看了。

**现在的设计。** 槽位**满了**之后，手牌里凡是「已经存在于被动系统内」的组合（触发板 × 已有该触发板下的某个效果板）**每帧自动升级一组**，多组命中时随机选；一次只吃一组。

**几个刻意的决定：**

- **挂在每帧，不挂在三处 `G.hand.push` 上。** 每帧调一次能覆盖全部拿牌路径（击杀掉落 / 商店买卡 / `grantCards` 批量发放），也顺带覆盖「槽位**刚刚**变满」那一刻。手牌 ≤20、被动 ≤7 组，一帧的代价可以忽略。
- **一次只宣读一组**（每帧一次），所以不会同一帧把 20 张手牌连锁清空、玩家什么都看不见。
- **槽位没满时直接返回 null**，行为与手动组合完全一致。
- 这两张牌是手牌里 `filter` 出来的**同一个对象引用**，`indexOf` 一定命中；两张不可能相同（一个是 trigger 一个是 effect）。

## 13. 教程：沙盒、石板顺序、字幕节奏

**为什么是纯沙盒。** 收尾字幕播完（或点「跳过教程」）走同一条 `restartRunAfterTutorial()`，把教程期间攒下的密文版 / 被动 / 精华 / 得分**全部清空**，回到第 1 层并重选一次职业。教程不再是「播完空降第 6 层」。

**为什么石板是这个顺序。** 闭环图腾（第 2 块）排在密文版（第 3 块）**前面**：判环只看轨迹本身，一张牌都没填时 `turType` 默认 `'basic'`——「画个圈就出一座塔」不需要先学密文版。

**为什么「敌人」与「核心」要拆成两块。** 属性三选一与节点地图都挂在 `G.floor % 5 === 0` 上，而收尾字幕必须等玩家在节点地图上选完路才播（`selectNode()` 里置的 `Tutorial.outroPending`）——**教程至少要走到第 5 层，收尾才有入口**。所以第 5 层不能提前结束。

**字幕节奏。** 两条提示的间隔 = **上一条 `hold` + 下一条 `d`**（`advance()` 把 `pendTimer` 清零，`triggered()` 再拿它和 `s.d` 比）。想让节奏落在 3 秒 ±1 秒，就是让这两个数配对：

```
hold + d ∈ [120, 240]     长句取上限，短句取下限
```

**⚠️ 改任何一句 `hold` 或 `d` 都要重新核对配对**——单看一个数字看不出节奏。

`on: 'move' | 'kill' | 'sprint' | 'clear' …` 这些是**事件门控**：玩家不动就不往下走，它们的实际间隔不受 `d` 支配（`d` 只在门开之后再加一层延迟）。

**手机端联动：** 教程步骤指向 `hand` / `combine` / `slot` 时自动展开左侧抽屉，该步骤播完自动收起——`Tutorial.drawerAutoOpened` 记住是「自己开的」才会去关。

**⚠️ 陷阱：脚本掉落是静默 no-op。** `dropScriptedCard()` 在 id 找不到时不会报错——漏改的表现是「**那一步永远等不到牌**」，不是崩溃。改那张表（例如第 5 层的脚本掉落）时务必核对 `TRIGGERS` 里真的有这个 id。

## 14. 性能：一帧预算与降负载

**一帧预算 16.67ms，主循环没有锁帧**——裸 `requestAnimationFrame`，帧率 = 显示器刷新率。越过这条线就落到下一个 vsync，也就是**恰好 30**。所以「30 FPS」出现的典型原因就是某一帧超了预算。

左上角常驻的读数 `30 FPS · U 1.2/3.1 · D 3.4/9.2 · 其他 28.7ms` 怎么读：

- `U` / `D` 是 `update()` / `draw()` 的 JS 耗时（500ms 窗口的均值 / 峰值）。
- `其他 = 1000/FPS − U − D`，装的是这一帧剩下的墙钟时间——GPU 光栅化与浏览器合成都算在这里（canvas 绘制是异步排队的，`draw()` 返回不代表画完了）。

| 现象 | 结论 |
|:--|:--|
| `U+D` 逼近 16.6ms | 瓶颈在 JS |
| `U+D` 小但「其他」大 | 瓶颈在绘制与合成 |
| 三项都小但帧率仍低 | 浏览器在限流，去看 `chrome://gpu` 的硬件加速有没有开 |

**降负载的两招：**

- **静态背景烘焙**：径向渐变 + 网格烘焙成一张 780×560 的离屏画布，每帧只 `drawImage` 一次（尺寸不变则复用同一张）。
- **`shadowBlur` 全面下调**：普通怪**不再用** `shadowBlur`，改一次光晕 `fill`；各类光晕也大幅下调。**只放过两处单实体**：玩家和 BOSS——全场只有它们各一个，`shadowBlur` 的代价与实体数成正比，这两处最值钱。
