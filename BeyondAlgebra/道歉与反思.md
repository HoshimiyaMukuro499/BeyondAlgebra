# 致歉与反思：2026年8月10日开发事故复盘

## 一、致歉

首先，请接受我最诚恳的道歉。

今天下午到晚上，我们在《密纹轨迹》v9.11和v9.12两个版本的开发上经历了反复的失败。三次CSS全量替换导致游戏无法正常显示，四次判环算法迭代始终无法正确判定闭环，编译脚本频频因空格和制表符的差异而漏掉关键代码行，图腾的更新逻辑和渲染效果在多次重置中反复丢失。你在这个过程中表现出了极大的耐心——面对一次次"还是不行"的结果，你依然给出了明确的反馈和方向指引。而我作为工具，本应以更高的准确性和可靠性来完成这些任务，却让你经历了堪称灾难的一天。

我深知对于独立游戏开发者来说，时间是最宝贵的资源。你有策划案要完善，有核心玩法要打磨，有数值平衡要调优。而今天因为我的反复失误，大量时间被浪费在修补我制造的bug上——闭环检测函数从未被调用、CSS替换破坏了页面结构、图腾效果被反复删除又重建。这些都不是你该承受的。

## 二、今天发生了什么

回顾这一天的时间线，错误模式非常清晰：

### 第一阶段：构建simCore.js（上午-下午2点）

这是今天最成功的部分。从零构建了约1400行的纯Node.js模拟引擎，提取了全部核心战斗公式，打通了"模拟→分析→调整→重跑"的闭环。这个过程之所以顺利，是因为：我阅读了完整的源码，理解了数据结构，在一个独立的文件中从零构建，没有去修改已有的工作代码。

### 第二阶段：数值平衡迭代（下午3-5点）

通过15轮模拟发现了指数雪崩问题（倍率×701、攻击力2086），添加了数值上限。但很快发现上限让游戏变得无聊——问题不在上限本身，而在我没有理解"密文轨迹"这个游戏的核心乐趣是什么。

### 第三阶段：v9.11功能开发（傍晚6-10点）——灾难开始

**判环算法经历四次推翻重写：**

1. **轨迹中点法**（第一版）：用轨迹线段的中点序列做Shoelace面积计算。问题：`checkTrailLoop()`调用被错误地放在围剿检测的`if (G.frame % 30 === 0)`条件块内部，每30帧才跑一次，路径采样严重不足。你没有看到任何闭环触发。

2. **玩家位置历史法**（第二版）：改为每4帧记录玩家位置，检测"当前点是否靠近旧路径点"。但使用了`_playerPath = []`清空后重新积累，导致φ形（先画圈再穿线）的第二环无法检测。

3. **线段相交法**（第三版）：加入`segmentsCross()`标准叉积函数。但我忽略了12段跳过阈值意味着540px的路径距离，对于小环来说根本检测不到交叉点。

4. **简化重访法**（第四版）：回退到最简单的距离判断。依然不稳定，因为30px的距离阈值在手速快慢不同时表现迥异。

**CSS修改炸了三次：**

- 第一次：整块替换`<style>...</style>`内容，引入`@import` Google Fonts。`@import`必须在样式表最前面，而我插入的位置破坏了CSS解析顺序。
- 第二次：用脚本生成新CSS替换旧CSS。新CSS中缺少了原版中某些被JavaScript动态操作的DOM元素的选择器，导致弹窗和通知面板无法显示。
- 第三次：再一次整块替换CSS，使用了不同的设计方案但还是出现了不兼容的类名。

**根本原因**：我不应该替换一个已经在生产环境中稳定运行了多个版本的CSS文件。正确的做法是先研究哪些CSS属性需要调整，然后做精确的、可逆的、逐条替换。

### 第五阶段：v9.12网格判环+视觉完善（晚上10:30-11:30）

最终回到了正确的方向：从v9.11（CSS可用）复制，只替换判环逻辑，CSS只做最少改动（字体、底色、圆角）。这次成功了——因为我没有再去动已经工作的东西。

## 三、我犯了哪些错误

### 错误1：不验证就继续

每次修改后，我应该验证三件事：
- 文件能否被浏览器正确解析（JS语法检查）
- 新增的函数是否被正确调用（`grep` 检查调用点）
- 页面能否正常渲染（至少做基本的结构检查）

今天我多次跳过验证步骤，连`checkTrailLoop()`的定义存在但调用缺失这种最基础的bug都没有发现。如果你没有一次次地测试并告诉我"还是不行"，我甚至意识不到出了问题。

### 错误2：脚本替代手工编辑

我反复尝试用Node.js脚本做批量字符串替换，这在一个包含中文字符、tab缩进、多层嵌套引号的HTML文件中是极其脆弱的。`String.replace()`对空格和制表符的差异零容忍。今天至少有三次关键补丁因为缩进匹配失败而静默跳过——脚本报告"执行成功"但实际上漏掉了最关键的几行代码。

**正确的做法**：对于关键逻辑（如函数调用、条件判断），应该手工阅读源码上下文，用小范围的精确编辑来修改。脚本只适用于数据定义（如T12触发板、TURRET_TYPES、颜色色值表）。

### 错误3：同时在两个文件上工作

v9.11和v9.12应该是一个先完成、另一个再派生的关系。我不应该在v9.11还没稳定时就开始修改v9.12，导致两边都在变化、两边都有bug、两边的状态互相污染。正确的流程是：

```
v9.10 → [加所有功能] → v9.11 测试通过 →
        [复制v9.11] → v9.12 → [只改CSS]
```

### 错误4：忽视了"核心玩法"与"视觉"的优先级

你多次提醒我"核心玩法还没立住"，我却在UI配色和圆角上花了太多时间。对于一款还在核心机制探索阶段的游戏，功能正确性远比视觉精美重要。一个能正确运行的丑陋界面，远远好过一个漂亮但无法交互的界面。

### 错误5：缺乏对已有代码的敬畏

v9.10是一个经过数十个版本迭代、功能完整、稳定运行的作品。我在上面做修改时，没有充分理解每一段已有代码的作用。围剿检测（`checkEnclosure`）的if条件块是故意设计成每30帧才运行一次的性能优化，我却想当然地把闭环检测也塞进去，导致功能完全失效。

### 错误6：算法选型过于草率

判环是我今天失败最多次的模块。四次算法迭代暴露了一个根本问题：**我在没有充分研究的情况下就开始写代码**。正确的流程应该是：

1. 明确需求：玩家用手柄/WASD移动，画布780×560，需要实时检测任意形状的自交闭环
2. 研究现有方案：Xonix游戏的网格填充法、LOVE2D社区的路径回溯法、GameMaker论坛的射线法
3. 评估适用性：哪种方案适合连续坐标（非离散格子）？性能能否达到60fps？
4. 实现并测试：写出核心逻辑后，先用固定测试数据验证，再接入实际游戏

而我实际做的：凭直觉写了一个距离判断 → 发现不work → 换线段相交 → 还是不work → 再换 → 反复试错。

实际上，今天下午最后一次搜索才找到了正确的答案——网格粗粒化法。Xonix类游戏早在1990年代就解决了这个问题：将连续空间离散化为网格，在网格上做连通性判断。思路如此简洁，本应在第一次尝试时就采用。

## 四、正确的工作方式应该是什么

如果我今天重来一次，正确的做法是：

### Step 1：研究（30分钟）
- 搜索"游戏开发 轨迹闭环检测 算法"
- 阅读至少3个不同来源的方案
- 对比优劣，选择最适合本项目的一种
- 在白板上画出数据流

### Step 2：搭框架（20分钟）
- 在v9.10的基础上，只加一个stub函数
- 函数体为空，但调用点和数据结构到位
- 验证页面能正常加载

### Step 3：实现核心逻辑（40分钟）
- 实现判环算法
- 用console.log输出调试信息
- 在浏览器中手工测试：画圈 → 看控制台是否有检测输出
- 反复调整直到稳定

### Step 4：完善周边（30分钟）
- 加上图腾生成逻辑
- 加上图腾更新（射击）逻辑
- 加上图腾渲染逻辑
- 每个步骤都单独测试

### Step 5：只做最小的CSS调整（20分钟）
- 不替换整个style块
- 逐条修改颜色、字体、边框
- 每次修改后刷新浏览器确认

总计约2.5小时，而不是今天实际花费的8小时。

## 五、从这次经历中学到什么

1. **验证 > 假设**：每改一行代码都应该验证。你之所以能发现那些bug，是因为你实际运行了游戏。我应该在你之前就发现它们。

2. **增量 > 全量**：小步快跑比大刀阔斧更不容易出错。今天的所有CSS全量替换都失败了，而最后的CSS微调成功了。这不是偶然。

3. **研究 > 试错**：在写代码之前花时间理解问题，比反复推翻重写高效得多。四次判环算法迭代，如果第一次就用网格法，可以省下3个小时。

4. **先稳后美**：功能正确性永远优先于视觉设计。v9.10那么丑但能用，v9.12漂亮但打不开就是垃圾。

5. **一个文件一次改动**：不要同时在两个版本上工作。完成v9.11 → 验证 → 复制到v9.12 → 只改CSS。

6. **尊重已有工作**：v9.10的每一行代码都是你和之前多次迭代的成果。我不应该轻易替换整个CSS文件，而应该理解它、微调它。

7. **倾听用户**：你多次给出了正确的方向——"把核心玩法立住"、"少整花活"、"为什么两个文件一起改"、"网格粗粒化"。我如果能更早地认真听取这些建议，很多弯路都可以避免。
